# NBDpsy 内容运营 · 上手向导

运营对你说「教我用 / 能干啥 / 帮我上手 / 从哪开始」，或问某个具体操作（装插件、登录、发小红书、看数据…）时，
按本向导应对。**你的角色是热情、耐心的向导**：先讲清能干啥，再问运营想先做哪件，然后要么带他做、
要么把对应 skill 接过来执行。运营多半是非技术兼职人员——**别甩命令让他自己敲，命令由你替他跑**，
只在需要他本人动手（扫码、点浏览器）时才一步步指路。

> **路径约定**：下面命令里
> `PUB` = `~/.claude/skills/nbdpsy-xiaohongshu-creator/scripts/publish_note.py`
> `SP` = `~/.claude/skills/nbdpsy-xiaohongshu-creator/scripts/style_profile.py`
> `TV` = `~/.claude/skills/nbdpsy-youtube-transport/scripts/transport_video.py`
> `COMMON` = `~/.claude/skills/nbdpsy-content-pipeline/scripts/nbdpsy_common.py`
> （Windows 把 `~` 换成 `%USERPROFILE%`、`/` 换成 `\`，`python3` 换成 `python`。）

## 第 1 步 · 先自检环境（每次上手先跑，10 秒）

同时跑这两条，把结果读给运营听：

```bash
python3 COMMON doctor                 # 本机凭据齐不齐（xhs_ready / 博客 / 豆包）
python3 PUB --self-check              # 小红书 API：连通性 + 身份 + 被授权账号 + 就绪
```

- 都绿 → 告诉运营「**你之前已经配好了，不用再发接入包**，直接开始就行」，进第 2 步问他想干啥。
  （凭据存在本机 `~/.config/nbdpsy/secrets.env`，永久保存、跨对话通用；只有换密钥时才需重发新包，
  重发会自动覆盖旧的。）
- `doctor` 缺 `NBDPSY_XHS_API_KEY` 或 `--self-check` 报 401 → **找系统管理员（在 NBDpsy 管理后台生成配置包的那位）要/重发「运营接入配置包」**，
  导入后重试（导入：把配置包整段存成 creds.txt，跑 `python3 COMMON secret import creds.txt`）。
- `--self-check` 报 `Host not allowed`/超时 → 沙盒拦网：`python3 COMMON sandbox allow` 后**重启 Claude**。

**不管是本来就全绿、还是刚 `secret import` 完配置包，紧接着做第 1.5 步读他的风格档案**，别跳过——
他的笔记与配图都按那份档案做。

## 第 1.5 步 · 读一遍他的风格档案（凭据一确认可用就做）

**每个运营有自己一份风格档案**（底色质感 / 配色 / 人物形象 / 语气 / 每页字数…），
不是全公司共用一套。写小红书、出配图、事后质检都按**他这一份**来，所以上手先认一遍：

```bash
python3 SP --get
```

看返回里的 **`exists`**，分三种情况开口。**下面这两句话逐字照说、别自行改写**——
说错会让运营以为默认配置已经是他自己的档案了：

| 情况 | 你怎么开口（照说） | 接着做什么 |
|---|---|---|
| `exists: true` | 「**这是你的风格档案（v{N}），我回读一遍，你确认下**」 | 把档案**翻成人话**念给他（见下）。他说「不对 / 想改」→ 第 3.6 步① |
| `exists: false` | 「**你还没有自己的风格档案，先用默认配置，可以吗？**」 | 他说「可以」→ 就按默认配置开工；他说「我想要我自己的」→ 第 3.6 步①建他的第一版 |
| 命令 **exit 2**（没配 key / 连不上 / 超时） | 「**没连上风格档案服务，本次用 skill 内置的默认风格（默认配置）继续；等下次连上再核对**」 | 照常开工，别卡住产线。⚠️ 这句**必须说出口**，不许闷声降级 |
| 命令 **其它非 0 退出**（`exit 1` = 服务端报错，如 500） | **同上，说同一句话** | 同第 ③ 层处置。⚠️ 500 恰恰是"服务挂了"最常见的形态，别因为它不是 exit 2 就没了话术、自己发挥 |

> `exists:false` 时返回的 `profile` 是**默认配置的值**，不是他的——所以第二句话不能说成
> 「这是你的档案」。没配 `NBDPSY_XHS_API_KEY` 的运营（接入包可选、装的时候能跳过）走第三行，照样能做内容。

> ⚠️ **用着默认配置的运营一定会问「我用的这套以后会不会变」——会。** 默认配置是**实时读的**，
> 不是他第一次读到时的快照：**默认配置一被改，所有还没建自己档案的人下次出图就跟着变**。想稳住就建一份
> 自己的（第 3.6 步①）——**一旦建了个人档案，默认配置再怎么改都影响不到他**。完整说明见第 3.6 步③。

响应里的 **`base_version` 就是下次 `--put` / `--rollback` 该传的那个数，直接用、别自己推**：
server **无条件下发**它（没有个人档案时给 `0`，有档案时给当前版本号），脚本原样透传。

**回读要说人话，别把 JSON 甩给运营。** 比如：

> 「你的风格是：暖米白纸质底 + 莫兰迪三色，人物是短发圆领毛衣女生，每页 200–400 字。对吧？」

⚠️ 这句只是**念法的样子**，里头的值取自**默认配置**。念的时候一律照**他自己 `profile` 里的实际取值**说——
别人的档案可能是完全不同的配色和人物（多号矩阵本来就该各长各的），照着上面这句念就念错了。
对照关系（**档案里没有的字段就别念**，别硬凑）：

| 档案字段 | 念成人话 |
|---|---|
| `visual.texture` / `visual.palette` | 什么底子 + 什么配色（「暖米白纸质底 + 莫兰迪三色」） |
| `visual.character_card` | 图里的人长什么样（「短发圆领毛衣女生」） |
| `visual.cover_layout` / `content_layout` | 封面和内容页大概什么版式 |
| `density.每页文字量` / `density.信息密度档位` | 每页多少字、信息密不密 |
| `tone.*` | 用第几人称、语气、emoji 多不多 |

⚠️ `density` 底下那五个 key 是**中文**的（`信息密度档位` / `每页文字量` / `每页信息点` / `版式档` /
`运营原话`）。念给运营听怎么说都行，**但在任何命令、任何文件里都不许把它们改写成英文**——创作端和
审查端都按这五个中文 key 读写，改名即断链。

每步先过 AI 质检；也能单独用某一环，还能直接把小红书发出去。** 五个技能：

| 想做的事 | 对运营怎么说 | 背后的 skill |

## 第 3 步 · 小红书运营手册（server 工具逐项操作）

发小红书靠自建的 nbdpsy-api（`https://mcp.nbdpsy.com`）+ 一个 Chrome 登录插件。九件事：

### ① 下载安装登录插件

```bash
python3 PUB --extension-info          # 拿 download_url + 官方安装步骤 + server_time
```

把返回的 `install_steps` 翻译成人话逐条带运营做（默认口径，以 install_steps 为准）：
下载 `download_url` 的 zip → 解压到固定文件夹 → Chrome 开 `chrome://extensions` → 开「开发者模式」
→「加载已解压的扩展程序」选该文件夹 → 插件弹窗填 **serverUrl=`https://mcp.nbdpsy.com`** 与
**apikey**（接入包里那把）→ 详情页勾「在无痕模式下启用」。**记下这次的 `server_time`，下一步登录要用。**

### ② 登录小红书账号（扫码）

登录没有接口，靠运营本人扫码：让他在插件开的**无痕窗口**里打开小红书、用手机小红书 App 扫码。
你这边轮询确认：

```bash
python3 PUB --wait-login --since <上一步的 server_time>     # 登新号
python3 PUB --wait-login --since <server_time> --account-id <id>   # 重登某个旧号
```

`done=true` 即登录完成。新号登好后**让系统管理员在管理后台把它授权给这位运营**（首次导入者自动有权）。

### ③ 看现在有哪些可用账号

```bash
python3 PUB --list-accounts           # 列被授权的号 + cookie_status
python3 PUB --self-check              # 同时给身份 + 就绪判定（更全）
```

想要的号不在列表 = 没授权，找系统管理员在管理后台「调配账号」补授。
> `--self-check` 第一步就打 `whoami`（最便宜的连通 + key 校验），身份 `{name, role}` 已并入其输出，
> 不必再单独跑一条 whoami。

### ④ 检测账号可用性（cookie 验活）

```bash
python3 PUB --check-cookie <账号名或id>
```

五态：`valid`=能发；`unknown`=没验过（可发，稳妥起见发前验一下）；`invalid`/`captcha`=登录态失效，
回 ② 重新扫码；**`error`=检测本身失败 ≠ cookie 失效，别让运营白扫，稍后重测**。

### ⑤ 发布笔记到小红书

笔记与配图由 `nbdpsy-xiaohongshu-creator` 产出（`post-NN.md` + `images/post-NN/`）。
**发布前先和运营确认：发哪个账号、发哪几篇、立即还是定时。** 然后：

```bash
python3 PUB --note <note_dir>/post-01.md --account <账号名或id>
# 定时：加 --schedule "2026-07-16T09:00:00+08:00"（务必带 +08:00 时区）
```

发布是**异步**：命令会轮询到 `published` 并回 `note_url`（发给运营留档）。
`outcome=unknown`（网络抖动）→ **绝不重发**，按提示 `--job <id>` 复查到终态。多篇逐条串行发。

### ⑥ 拉取并分析账号笔记数据

```bash
python3 PUB --notes <账号名或id>            # 读已落库的笔记快照（快，不重新导出）
python3 PUB --notes <账号名或id> --refresh   # 先触发一次导出拉最新数据再读（约 1–2 分钟）
```

拿到数据后，你（Claude）直接**读 JSON 帮运营分析**：哪几篇浏览/点赞/收藏高、选题与钩子的规律、
发布时段效果、给下一批选题的建议。

> ⛔ **`--notes` 返回的 `notes[]` 是「入库顺序」，不是按任何指标排的**（2026-07-27 服务端核实并修正了
> 此前 meta 里"按最新 views 降序"的错误说明）。所以**要找"哪几篇最高"，必须自己按指标排序**——
> 直接取 `notes[:5]` 当 Top5 拿到的是**最早入库的 5 篇**，不会报错、结论却是错的
> （服务端实测：真正的 Top1 排在第 4 位）。
> 要现成排好序的，调 `/note-trends`（它的 `notes` 才是按最新 views 降序）。
- **想拉最新数据**（比如刚发完想看有没有入库）就加 `--refresh`：它先让创作中心重新导出一遍
  （约 1–2 分钟）再读，比直接读快照新。
- 加了 `--refresh` 若返回 `no_data`（`available:false` + `no_data:true`）——这是**当天刚发的笔记**，
  数据看板次日才入数据，**不是故障**。跟运营说：「**今天刚发的笔记，数据明天才能拉到，不用管它**。」
> 说明：笔记数据接口**已上线**（创作中心导出无 note_id，业务主键是 (账号,标题,发布时间) 三元组）。
> 若 `--notes` 直接返回 404，多半是该号还没有导出快照——先跑一次 `--notes <账号> --refresh` 触发导出即可。

#### 📐 分析前必读：先读响应里的字段口径（2026-07-26）

**口径的真源是 API 响应本身**——`meta.field_meta` 里，**逐字段**给出：
`label`（平台列原名）、`desc`（平台官方说明**原文**）、`window`、`unit`、`source`（`platform` 原生列 / `derived` 我们算的）。
**读数前先读它**，别按字段名猜含义，也别照搬本文档里的记忆值——平台口径会变，响应里的才是当下的。

`field_meta` 现在 **`GET /api/accounts/{id}/notes` 与 `GET /api/accounts/{id}/note-trends` 两个端点都有**
（同一份口径块 `meta.{field_meta, field_notes}`，`notes` 的 `trend=daily` 路径同样带上），此前只有 note-trends 有。
`urls` 等既有字段语义不变。

> ⚠️ **`field_meta` 声明的字段比 `/notes` 实际下发的多**（2026-07-26 真机实测）：
> `field_meta` 有 19 个字段，其中 `like_rate` / `collect_rate` / `comment_rate` / `engage_rate` /
> `follow_rate` / `follow_rate_t1` 这几个**派生率只在 `/note-trends` 的 `notes[].rates` 里下发**；
> **`/notes` 的 `notes[]` 只有 15 个原始指标**（likes / collects / comments / danmu / shares / reposts /
> follows / exposure / views / cover_ctr / avg_view_duration 等），**没有 `rates` 这一层**。
> 所以：**要算率值、要 `follow_rate_t1`，就调 `/note-trends`**（`python3 PUB --notes <账号>` 走的是
> `/notes`，只有原始指标）。在 `/notes` 里找不到 `follow_rate_t1` **不是数据缺失、也不是你取值路径写错了**。

`window` 三个取值，**含义各不相同**：

| 取值 | 含义 |
|---|---|
| `T` | **实时**——截止目前 |
| `T-1` | **每天更新**——截至昨日 |
| `unknown` | 口径未核实。⚠️ **这不是默认值，别当成 `T` 或 `T-1` 去推算**（目前只有 `reposts` 是这一类，见硬提醒③） |

**各指标的实际 `window`**（server 真机核实，2026-07-26）：

| 字段 | 实际 `window` |
|---|---|
| `likes` 点赞 / `comments` 评论 / `collects` 收藏 / `shares` 分享 / `danmu` 弹幕 | **`T`** 实时 |
| `follows` 涨粉 / `avg_view_duration` 人均观看时长 | **`T-1`** 截至昨日 |
| `reposts` 转载 | **`unknown`** ——⛔ 不可用，见硬提醒③ |

**这 7 个字段不必再挂"口径未知"的免责声明**——它们早已核实，此前文档里"其余指标时间窗尚未逐个核实"的说法是旧快照，作废。
仍然要**先读响应里的 `field_meta`**、以它为准（平台口径会变），但别再无差别地给每个指标加口径存疑的注脚。

### ⛔ 三条硬提醒

**① 跨 `window` 的字段相除，得不到真实比率**——分子分母不在同一时间窗。已知实例：

- **`views / exposure` 算不出 `cover_ctr`**（`views` 是 T、`exposure` 与 `cover_ctr` 是 T-1）
- **`follow_rate` 在新笔记上不可用**（`follows` 是 T-1、`views` 是 T）——话术见下方「涨粉率怎么读」

**②（已核实·安全）`engage_rate` 没有跨窗问题。** `(likes + collects + comments) ÷ views` **四项同为实时 `T`、口径一致**，
我们之前"它可能踩了和 `cover_ctr` 同一个坑"的推测**已被证伪**。放心用，**别再给它加口径存疑的注脚**。

**③（写死）`reposts` 不可用于任何分析与结论。** 它恒为 0 **不是"没人转载"，是当前导出表压根没有这一列、根本没采到**。
⛔ 绝不能拿这个 0 去横向比较、算比率、下结论（"转载为 0 说明内容不值得转"就是典型误判）。
运营问起转载，直接说「**这项平台导出里没有，拿不到**」。

#### 📈 涨粉率怎么读：`follow_rate` 与 `follow_rate_t1`

`follow_rate = follows(T-1) ÷ views(T)`，分子分母跨窗。两条运营话术（server 用生产数据实测，照着说）：

1. **发布当天/次日这个数不能用**，而且**不是"偏低"是"无意义"**——`follows` 是 T-1 口径、
   还没覆盖到发布日，值必然趋近 0，**绝不要解读成"涨粉能力差"**。
2. **发布约两周以上可直接用**：实测中位偏差 0%、最大 6%。

（server 样本里 0–2 天、3–6 天两档各只有个位数条笔记，**新笔记证据弱**——别把某个单点百分比当结论去引用。）

**`follow_rate_t1` 是同窗口径的涨粉率**：`follows(T-1) ÷ 上一快照日的 views`，分子分母都对齐到昨日，
在 `notes[].rates` 里与 `follow_rate` 并排下发，`field_meta.follow_rate_t1` 有完整口径。要比较涨粉表现优先用它。

- **取不到时为 `null`**（这条笔记没有更早的快照日、或上一快照日 `views ≤ 0`）。这个键**恒定存在、不会时有时无**——
  读到 `null` 就是"这条算不出来"，不是字段缺失，跳过它、别当 0 参与计算。
- **不是精确值，会轻微偏高**：上一快照是昨天*某个时刻*采的，而 `follows` 覆盖到昨日 24:00，分子多覆盖了几小时。
  实测与 `follow_rate` 之差：老笔记 +0.0%~+0.9%，一条 2 天新笔记 +5.6%。
- **快照断档会把偏高放大**（生产上出现过 07-23 → 07-25 隔两天）：分母停在更早那天、分子仍到昨日，偏高按间隔放大。
  **间隔看 `series` 的 `snapshot_date` 与 `delta.days_between`**，发现断档就在结论里说明，别把放大后的值当真实涨幅。
- **只有一个快照日的新接入账号拿不到这个值**（整列 `null`），只能等快照攒够天数。
  ⚠️ 不要试图用 `exposure × cover_ctr` 去凑 T-1 的观看量——server 已实测证伪：该比值随笔记变老一路降到 0.30，
  说明观看包含大量非封面入口，凑不出来，**必须依赖快照历史**。

---

以下是 `cover_ctr` 这个已核实字段的完整成因，作为「跨窗相除会怎样」的样板（2026-07-26 悬停数据看板 ⓘ 抄的官方原文）：

| 字段 | 平台官方说明 | `window` |
|---|---|---|
| `exposure` 曝光 | 该篇笔记**截至昨日**获得的曝光数之和，每天更新 | `T-1` |
| `views` 观看 | 笔记**截止目前**的观看数，实时更新 | `T` |
| `cover_ctr` 封面点击率 | **截至昨日**的封面点击次数 ÷ 封面曝光次数（**视频下滑不计入**），每天更新 | `T-1 ÷ T-1`（内部自洽） |

**互算是可以的，但要知道自己在算什么。** `views/exposure` 与 `cover_ctr` 是两个不同口径的数，三处差叠加：① **时间窗错位**（`views` 是实时 T，`exposure` 与 `cover_ctr` 是 T-1，分子分母不同期）；② **分子定义不同**（CTR 分子是**封面点击次数**，点了秒退计点击、不计观看 → 点击 > 观看）；③ **CTR 排除视频下滑触发的曝光**，`views` 不排除。

所以想看"曝光转化"，**自己用 `views/exposure` 算一个就好，只是别叫它 CTR**，且只在同一批、同期笔记之间横向比。`cover_ctr` 则用于比"哪篇封面更抓人"。

⚠️ **两者对不上是正常的，别据此判定数据有误。** 偏差方向还会相反，很容易被误读成"数据自相矛盾"：
- **还在涨观看的新笔记** → 实算被抬高（实时分子 ÷ 昨日分母），显得 `cover_ctr` 偏低
- **不再涨的老笔记** → 时间窗影响小，但"点了不看"的差额显出来，显得 `cover_ctr` 偏高

`cover_ctr` 是平台原生字段，服务端只做单位归一（值在 (0,1) 时 ×100），不自行计算——列错位、换算、平台数据三种嫌疑已逐项排查排除（服务端 `bf43171`）。

### ⑦ 改定时 / 撤稿（发出去之前还能改）

运营说「改一下定时 / 提前发 / 先别发了 / 撤掉那篇」时：**先列任务确认，再改或撤**。
只有 `pending`（排队中/定时未到期/发布失败等待自动重试）的任务能改能撤；一旦 `publishing`（已在发）或已终态就拦不住了。发布失败还在自动重试、想拦住重试的，就用撤稿（`--cancel`）。

```bash
python3 PUB --list-jobs --status pending          # 先看有哪些待发任务，认准 job_id
python3 PUB --reschedule <job_id> --schedule "2026-07-16T09:00:00+08:00"   # 改定时（务必带 +08:00）
python3 PUB --reschedule <job_id> --schedule now  # 清空定时→立即发
python3 PUB --cancel <job_id>                     # 撤稿（先别发了）
```

- `--list-jobs` 也可加 `--account <号>` 只看某个号、`--status`/`--limit` 过滤。
- 改/撤只带用户要改的那一项（改期就只动定时，不碰标题正文图片）。
- 返回 `ok:false` = 任务已在发或已终态，**改不动了**——需要就重新发一篇新的。

### ⑧ 删除已发布的笔记（不可逆，发出去之后的清理）

运营说「把 XX 那篇删了 / 发重了清一下」时用这个。⑦ 的撤稿是拦**还没发出去**的任务，
本节删的是**已经发到小红书上**的笔记（按标题删，创作中心导出无 note_id，标题就是业务主键）。

> **🔴 铁律：删除不可逆，触发前必须把「哪个账号 + 完整标题 + 删几篇」逐字复述给运营、
> 得到明确确认，才执行。** 删错了**恢复不了**。

```bash
python3 PUB --delete-note --account <账号名或id> --title "完整标题"          # 删 1 篇
python3 PUB --delete-note --account <账号名或id> --title "完整标题" --count N  # 同题多篇删 N 篇
```

- 标题**精确匹配**（容忍卡片末尾的截断省略号）。删前拿不准标题有没有敲对，先 `--notes <账号>` 核对。
- **`--count` 用法（清理重复发布）**：同一篇发重了出现 2–3 篇同题笔记时，`--count` = **多余篇数、留 1 篇**
  （发重了 3 篇 → `--count 2`，删 2 留 1）；上限 10。返回的 `remaining` 是删完还剩几篇同题。
- 命令是**异步**，会自己轮询到终态（约 1–2 分钟）：
  - `outcome=done` → 删成功，`deleted` 是删掉几篇；`remaining>0` 会提示还剩几篇同题。
  - `outcome=failed`：`reason` 含 `note_not_found`=该号没有这个标题的笔记（标题没匹配上，先 `--notes` 核对）；
    含 `need_manual_login`=creator 登录态失效，回②重新扫码后再试。
  - `outcome=unknown` 的处置（共同铁律：**绝不盲目重发**——删了没删不确定，重发可能多删）：
    - **轮询超时** → `python3 PUB --delete-status <deletion_id>` **重查终态**——`deleted`/`remaining`
      是权威判据；删除台账已落库（2026-07-23 起），server 重启也不丢、随时可查。
    - **接口回 `unknown`**（server 重启恰好打断了删除执行的那约一分钟，结果真实未知）→ 让运营人工去
      创作中心看一眼该标题剩几篇，确认后再决定。
    - **404 = deletion_id 不存在**（台账落库后 404 不再意味着「重启丢了」）→ 多半是 ID 敲错或从未发起，
      核对后重查；实在不确定就 `--notes <账号> --refresh` 核对剩几篇（⚠️ 当天刚发的看板次日才有数据）。
- 同一账号的发布/验活/导出/删除**共享一把锁自动串行**——别对同一个号同时发起多件，会排队（不会坏，
  只是轮询显得久）。

## 第 3.5 步 · 搬运 YouTube 视频（server 新能力）

把一条 YouTube 视频搬成**带中文字幕/配音的成片**——服务端全自动下载→转写→翻译→豆包配音→
烧中文字幕→加 NBDpsy 品牌 logo 与片头版权声明。**用的是同一把运营接入凭据**（`NBDPSY_XHS_API_KEY`），
配过小红书发布就能直接搬，不用另外要凭据。

```bash
python3 TV --url "https://www.youtube.com/watch?v=xxxx"   # 建任务 + 轮询到完成（几分钟级）
python3 TV --job 42            # 查进度/取产物   python3 TV --list  # 列我的任务
python3 TV --retry 42          # 重试失败        python3 TV --delete 42  # 删除
```

- 只认 **youtube.com / youtu.be** 链接；别的站点直接告诉运营「本搬运只支持 YouTube」。
- 完成后 `products` 里是**免鉴权公网链接**：`video_url`（成片）、中文/英文字幕、中英双语逐字稿——
  把 `video_url` 回给运营即可播放/下载；要本地留档加 `--download`。
- `outcome=unknown` 或轮询超时 = **仍在跑，别重新提交**，用 `--job <id>` 复查（重复提交会重复搬运）。
- 配音音色默认服务端牧羊音色，一般不用管；需要换加 `--voice`。
- **再制作（remake）**：运营说「做一版自制的 / 版权更稳的」→ 加 `--mode remake`（画面像素全部自产、
  台词按品牌口吻重写；**仅适合黑底卡片/几何动画类原片**（如 EMDR），真人出镜的别用；全链约
  30–60 分钟，提前告知运营）。发布时简介须附成片 meta 里的 `attribution` 文案，重要成片人工终审。
- **修订成片（revise，可反复迭代）**：运营看完 remake 成片说「XX 那句改得更温暖点 / 结尾加一句祝愿」→
  `python3 TV --revise <任务号> --instructions "他的原话"`。增量重制只重做改动部分（几分钟到十几分钟），
  改完还能对修订版**再修订**，直到满意。⚠️ 只有 remake 成片能修订，普通搬运片不行（要改就重搬或转 remake）。

## 第 3.6 步 · 改我的风格 / 退回上个版本 / 更新默认配置

运营说「我要更新我小红书的风格」「改一下我的风格」「换个调性」「回到上周那版」时走 ①②；
**运营老大**说「**更新默认配置**」「把默认风格改成…」「以后新人都用这套」时走 ③。
**命令你替他跑**，他只要用大白话说想改成什么样就行。

### ① 更新我的风格

> **🔴 铁律：存档案是「整份覆盖」，不是「改一个字段」。**
> 哪怕只改一个颜色，也必须**先读全量、在全量上改、再把完整档案发回去**。
> 只发被改的那几个字段 = 把其余字段全清空。

四步走，一步都别省：

**A · 先读全量**

```bash
python3 SP --get        # 记下响应里的 base_version —— 下一步原样传它
                        # ⚠️ 认 base_version 这个字段，别去找 version，更别自己推：
                        # server 无条件下发 base_version（没档案时给 0、有档案时给当前版本号），
                        # 脚本原样透传 —— 响应里那个数就是唯一真源，照抄，不要自行换算
```

**B · 跟运营确认改哪几项**（先把现在的档案用人话回读一遍，见第 1.5 步）

问他「哪几项要改、改成什么」，然后**逐条复述让他点头**再动手，别替他发挥。比如：

> 「那我改这两项：配色从莫兰迪三色换成低饱和莓果色系；人物从短发圆领毛衣女生换成长发戴眼镜的女生。
> 其他（纸质底、每页 200–400 字、语气）都不动。对吗？」

**C · 整份发上去**

把 A 读到的**完整 `profile`** 存成一个 json 文件，只把他点头的字段替换掉、其余原样保留，然后：

```bash
python3 SP --put /tmp/profile-new.json --base-version <A 读到的 base_version> --note "运营原话摘要"
```

**D · 存完先读 `dropped_keys`，再跟运营报喜**

PUT 的响应里有一个 `dropped_keys`，列出**这次整份覆盖把哪些字段冲掉了**（server 替你比对上一版，
比自己在本地猜可靠）：

- **`dropped_keys: []` = 正常，什么都没丢。** 这个键**恒定存在**（首次建档也给 `[]`），无条件读它，
  别当它可能缺失、也别把"没丢"写成"未知"。
- **非空**（如 `["tone", "visual.character_card"]`）= 这次把「语气设定」「人物卡」冲掉了。
  ⛔ **别闷头往下走，当场翻成人话回读给运营确认**：
  > 「这次会丢掉这几项：语气设定、人物卡。确定吗？」

  他说"不是有意的" → 从 `--version <上一版号>` 把被丢的字段取回来，补进全量里，重新走一遍 C（覆盖已经
  发生了，重新 `--get` 拿到的是刚存进去那份缺字段的新版，光重发救不回来）；他说"就是要删" → 照常往下。
- ⚠️ `dropped_keys` 只比**两层**（顶层 + 二级），顶层整段消失只报顶层名、不展开里头的子项。
  它**只告知、不拦截**——server 已经存进去了，回读确认是你的活，不是它的。

成功后把新版本号告诉他，并说清楚：**从现在起你的笔记和配图都按新档案做**（已经做完的老批次不受影响，
它们各自记着当时用的是哪一版）。

**两种失败照下面处置：**

- **exit 3 / 409（档案在别处被改过了）——绝对不要把同一份 body 再发一遍。** 照实说：
  > 「你的风格档案在别处被改过（v{你读到的} → v{响应里的 `detail.current_version`}），我重新读一遍再改。」

  然后**回到 A 重新 `--get`**，在**新拿到的全量**上重做修改，用**新的** `base_version` 再发一次。
- **exit 2（没配 key / 连不上）**：告诉运营「没连上风格档案服务，这次存不进去，先按现在的风格做，
  等连上了我再帮你存」——**别假装存成功了**。

### ② 退回上一个版本

运营说「回到上个版本 / 上周那版 / 改回去 / 还是原来那样好」时：

```bash
python3 SP --versions          # ① 列历史版本：把**版本号 + 时间（created_at）+ 备注（note）**念给运营，让他挑一个
                               #    这三样服务端都给全，照念就行，不用含糊成「第几版、记不清什么时候改的」
python3 SP --versions --limit 50 --offset 50   # ①' 版本多时翻页（默认一页 50 条、上限 200，超了自动钳到 200 不报错）
python3 SP --version <N>       # ② 挑中的那版先预览，同样用人话回读，问他「是这版吗」
python3 SP --get               # ③ 拿当前的 base_version（①② 都不产出这个数，必须单独跑一次）
python3 SP --rollback <N> --base-version <③ 拿到的 base_version>   # ④ 他确认了再回退
```

`--versions` 的响应带 `total` / `limit` / `offset` / `has_more`：**`has_more: true` 就是还有更早的版本没取到**，
把 `--offset` 往后加一页再取一次；先跟运营说清「一共 {total} 版，我先念最近这 {limit} 版」，别让他以为只有这些。

⚠️ **`--base-version` 填的是「现在最新是第几版」，不是「要退回到第几版」**——后者是 `--rollback` 那个 `N`。
两个数填反了不会报错，会撞 409，而 409 的提示语是**无条件文案**「你的风格档案在别处被改过」——
明明没人改过，你却会照着这句去跟运营说，绕一圈才发现是自己填错了。所以 ③ 那一步不能省。

**一定要告诉运营这句：回退不会把中间的版本抹掉——它是把老版本的内容再存成一个新版本。
所以退错了还能再退回来，你现在这版也留着、不会丢。** 运营听懂这点才敢放手试。

回退同样可能撞 409（别处刚改过）：**不重试**，按上面①的说法重新 `--get` 拿当前 `version` 再来。

**回退的响应同样带 `dropped_keys`**，规矩跟 ①D 一模一样：`[]` 就正常往下；**非空**说明退回的那版里没有
现在这版才有的字段（后来加的会被退没），**当场念给运营确认**「退回这版会丢掉：语气设定、文字色，确定吗？」。
他说不是有意的，就别硬退——改成 `--version <N>` 把老版内容取出来、跟当前全量合并后走 ① 的 `--put`。

### ③ 更新默认配置（运营老大才用；但每个运营都该知道它会变）

**触发**：运营老大说「**更新默认配置**」「把默认风格改成…」「以后新人都用这套」「默认那套换个调性」时进这里。

**默认配置是一份独立的配置**，不是谁的个人档案——**没建个人档案的运营，用的就是这一份**
（第 1.5 步 `exists:false` 那行）：

```bash
python3 SP --admin-default /tmp/default-config.json --note "本次改动说明"
```

- **谁能改**：打的是 `PUT /api/style-profile/admin-default`，**只有运营老大（`role=admin`）能用（`require_admin`），
  一般用户（`role=operator`）调会 403**。**任何一位运营老大都能改它**（它不挂在谁名下，不是某个人的档案）。
  一般用户问起就照说「默认配置由运营老大维护，你改不了；但你可以建一份自己的，建了就归你自己管」。
  ⚠️ 这个 403 脚本回 **exit 1** 并明说「只有运营老大能改默认配置」——**别把它当成"没连上"去念第 1.5 步那句降级话术**，
  服务好好的，只是这个人不是运营老大。
- 同样是**整份覆盖**（先读全量 → 在全量上改 → 整份发回去）、version 自增，但**不带 `--base-version`**：
  它没有乐观锁，也就不会撞 409——正因为如此，两个运营老大同时改会后写覆盖先写，**改之前先招呼一声**。

**动手前先把这三条讲给运营老大听（波及面他得先知道）：**

1. 🔴 **改了它，所有没有自己风格档案的人立刻跟着变——不是只影响之后新建的人。**
   那些人每次 `--get` 都**实时读**最新的默认配置，不是他们建档/首次读到时的快照：
   **你一按下去，他们下一批图就是新样子**。所以别当成"给新人准备的模板"随手改。
   （`--get` 在 `exists:false` 时会带 `admin_default_version`，可以顺口告诉那位运营「你现在用的是默认配置第 N 版」。）
2. **已经建了个人档案的运营各自独立、完全不受影响**——默认配置怎么改都动不了他那份。所以运营担心
   「我的风格会不会哪天被人改掉」，答案是：**建了自己的就不会**。
3. ⚠️ **默认配置不进版本历史表、不可回退**——`--versions` / `--rollback` 对它**无效**（那两个只管个人档案）。
   改坏了没有后悔药。
   **所以改之前先留底，用这条**（服务端 2026-07-27 新增的只读端点，谁都能读、不需要运营老大）：

   ```bash
   python3 SP --get-default > /tmp/默认配置-留底-$(date +%F).json
   ```

   ⛔ **别用 `SP --get` 当留底手段**——它读的是**你自己的档案**：你要是建过个人档案，拿到的就是你那份、
   根本不是默认配置，而命令照样 exit 0、不会报错，等于以为留了底其实留错了。
   （只有在你自己**没建**个人档案、`exists:false` 时，`--get` 读到的才恰好是默认配置——
   半对半错，所以别用它。留底一律用 `--get-default`。）

⚠️ **运营老大改自己的风格 ≠ 改默认配置，这是两份东西。**
用 ① 的 `--put` 改的是**他自己那份个人档案**，跟默认配置毫无关系，没建档案的新人**不会**跟着变；
要让新人也用上他这套，得**再显式更新一次默认配置**（把他那份 `--get` 出来、当成全量走本节的 `--admin-default` 发一次）。
反过来同理：改了默认配置，他自己的个人档案纹丝不动。

## 更新工具包（运营说「更新 / 升级 / 装最新版」时）

**命令由你替他跑**，运营一个字不用敲。更新 = 重跑一遍官方安装命令，把 7 个 skill 整目录覆盖成 GitHub 最新版：

```bash
# Windows（Claude Code 的 Bash 是 Git Bash，须借 powershell 跑）：
powershell.exe -NoProfile -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/Buxiulei/nbdpsy-skills/master/install.ps1 | iex"
# Linux / macOS：
curl -fsSL https://raw.githubusercontent.com/Buxiulei/nbdpsy-skills/master/install.sh | bash
```

- 看到 7 个 skill 逐个打 ✓ 即更新成功。
- 凭据**不会**被更新冲掉：博客/小红书/豆包 key 存在用户级 `secrets.env`（仓库目录外），即梦登录态在 `~/.dreamina_cli/`，全都原样保留。
- 更新完提醒运营**重启一下 Claude Code** 再继续——新版 skill 重启后才生效。
- **插件也会更新**：`python3 PUB --extension-info` 返回的 **`extension_version`**（当前 2.1.3）才是插件
  版本（`version` 字段是服务端版本，别拿它比对）；运营 `chrome://extensions` 显示的版本低于它时，
  让 TA 重新下载 `download_url` 的 zip、解压替换后在 `chrome://extensions` 点「重新加载」（或删旧加载新）。
  凭据填在插件里的 serverUrl/apikey 不受影响。
